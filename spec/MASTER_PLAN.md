## 3. 후보 발굴과 증거 검증

1. **자료 등록.** 원본은 읽기 전용으로 보존한다. 프로젝트·저장소·PR 번호와 URL, 리뷰·댓글 ID, 커밋 SHA와 해당 버전의 파일·줄, 대화·메시지 ID와 화자, 작성 시각을 기록한다. 원본을 가져온 시각, 로컬 위치와 입력 해시를 별도로 남긴다. 가변 브랜치명만으로 특정 시점의 코드를 인용하지 않는다.
2. **대화와 코드의 양방향 연결.** 아래 3.1절의 제목만을 이용한 선분류를 먼저 적용한다. 본문 검토·검색 대상에 한해 ChatGPT 내보내기의 메시지 본문에서 프로젝트명, 파일·함수명, 오류 문구, 증상을 검색한다. 제목은 선분류 단서이며, 개발 경험이나 프로젝트 연결을 확정하는 근거는 제목에 의존하지 않는다. PR에서 대화를 찾고, 대화에서 단서를 얻어 Git 이력도 찾는다. 앞뒤 메시지, 시기, 코드 위치, 변경 내용을 대조한다. 한 대화의 여러 문제는 분리하고 여러 대화에 걸친 같은 문제는 원본 링크를 유지해 통합한다. 애매한 대화는 재검색 대상으로 남긴다.
3. **심층 조사.** 가치가 높거나 핵심 판단이 불명확한 후보는 최초 구현, 중간 수정·되돌림, 리뷰 당시 코드, 최종판을 시간순으로 재연한다. 각 시점에 알 수 있던 제약과 이후에 밝혀진 결과를 구분한다. 실패·폐기한 접근마다 선택 당시의 이유와 포기한 이유를 찾는다. 직접 기록이 없으면 근거가 지지하는 가설, 다른 가능한 설명, 반대 근거, 사용자 확인 질문을 남긴다.
4. **주장 단위 기록.** 후보 ID에 상황, 역할, 목표·제약, 고려한 옵션, 실제 행동과 결과를 연결한다. 각 주장에는 근거 ID와 작성 주체를 붙인다. ‘기록상 사실’은 원본에서 확인한 범위, ‘AI 추론’은 근거·불확실성·대안 설명, ‘사용자 확인’은 질문과 답변 원문·확인 시점을 담는다. 당시 기록과 사후 회고가 충돌하면 둘 다 보존한다. AI 제안의 실제 채택은 후속 코드나 명시적 확인을 찾는다.
5. **독립 검증과 짧은 기술 인터뷰.** 검증자는 주장과 원본을 새로 읽어 과장, 본인 기여 오인, 다른 프로젝트와의 혼동, 누락된 후속 변경을 점검한다. 가치가 높은 후보부터 당시 대안, 기각 이유, 역할, 검증 방법을 묶어 질문한다. 답하지 않은 질문은 비워 둔다. 불충분한 후보는 보류하고 새 근거가 생기면 다시 연다.

### 3.1. ChatGPT 자료 보관과 선분류 · 기존 파이프라인 확장

DATA-01~03은 Work 개정에 기록된 요구를 C00-A 사용자 요청으로 정본에 반영한 확장이다. 다음 계정·기간 정보는 기록된 사용자 제공 정보이며, 자료의 실제 구성·본문 열람·분류·수집 완료를 뜻하지 않는다.

- 논리 계정은 A/B로 구분한다. Work ZIP에 기록된 요구 경로는 `data/raw/chatgpt/account_A/`·`account_B/`이다. 현재 작업 공간에는 `data/raw/chatgpt/account_google/`·`account_csu/` 폴더가 존재하지만 A/B와의 대응은 확인 대기다. 경로명으로 계정 소유·동일성을 추정하지 않는다. 로컬 개정 사본의 경로 표기 변경 주체·원인·승인은 미확인으로 남기며 새 확정 요구로 채택하지 않는다. 이번에는 폴더·파일을 이동·이름 변경·복사하지 않는다.
- 계정별 원래 내보내기 파일은 확정된 계정 폴더 바로 아래에 두고 `extracted/`는 만들지 않는 보관 규칙을 유지한다. 내보내기에 포함된 자료의 원본 형식과 상대 경로를 보존한다. 실제 계정 대응·읽기 범위 확정과 해당 실행 승인 전에는 보관 경로를 적용하거나 본문을 읽지 않는다.

- 계정·대화·메시지의 출처를 구분한 채 두 계정을 논리적으로 통합 검색한다. 동일 제목이나 유사 내용만으로 원본을 합치거나 삭제하지 않는다. 계정별 구성·중복·누락 검토는 향후 승인된 단계에서 수행한다.

개별 경험의 점수와 개인 특성 분석은 따로 기록한다. 요구사항 누락·경계 조건 발견, 시스템 이해, 기술 전문성, 문제 정의, 사용자 관점, 기획, 계획·의존성 관리, 소통, 팀워크, 오너십, 학습·실패 대응을 조사한다. 서로 다른 PR과 프로젝트의 구체적 사례, 반례, 역할·환경 변화를 대조해 반복 행동이나 성장에 대한 해석의 범위를 정한다. 리뷰 횟수 자체로 판단하지 않는다.

새 Obsidian 폴더의 `vault/log/<프로젝트>/`에 개발 기록을, `vault/experience/<프로젝트>/`에 검증된 경험을 작성한다. 기존 개인 vault로 옮기는 작업은 나중에 사용자가 선택한다. 파일명, 섹션, frontmatter, 고정 어휘와 출력 순서는 [NOTE_TEMPLATES.md](NOTE_TEMPLATES.md)를 따른다. 실제 대안 비교가 있는 경우 decision으로 분류한다. Q&A의 ‘내 이해’와 꼬리 질문의 답은 사용자가 말한 내용만 쓴다. 상황·실제 행동·본인 기여·핵심 판단이 확인된 experience에만 발행 규칙의 verified 값을 적용한다. 가설, 점수, 미확인 후보는 노트 형식 밖에서 관리한다.

## 5. 정량 근거와 실험 승인

당시 측정 기록이 있으면 원자료와 조건을 확인한다. 기록이 없고 재측정할 가치가 있으면 대상 지표, 비교할 이전·이후 SHA, 환경·의존성·입력 규모, 실행 명령, 반복 횟수와 통계, 임시 파일 변경, 원복 방법을 먼저 제시한다. 해당 계획에 대한 사용자 명시적 사전 승인을 기록한 뒤에만 테스트 작성·실행, 코드 변경, 측정을 시작한다.

승인 범위 안에서 격리된 임시 복사본에 동일 조건을 적용한다. 원시 결과와 조건을 별도 보고서에 보관하고 지표에 맞게 중앙값이나 p95 등을 제시한다. 실행 실패나 조건 불일치는 기록하고 비교할 수 없는 수치는 비워 둔다. 완료·중단 시 실험용 파일과 환경을 원복·정리하고 원본 상태를 확인한다. 결과에 ‘현재 재현 측정’과 날짜를 표시한다. GitHub에 push, 커밋 업로드, PR·리뷰·댓글·이슈 작성 등 원격 쓰기를 하지 않는다.

## 6. 구현 설계 · 설계 유지 및 구현 상태 구분

| 기억 계층 | 담을 자료와 수명 |
| --- | --- |
| L0 공통 규칙 | 최신 명세, 템플릿, 승인 범위. 매 작업 시작 시 읽는다. |
| L1 영구 근거 | GitHub·ChatGPT 원본 JSON과 버전별 코드, 주장↔근거 관계. 원문을 다시 조회할 수 있게 보존한다. |
| L2 작업 상태 | 프로젝트별 인벤토리, 후보, 큐, 단계, 승인·보류 사유, 체크포인트를 디스크에 저장한다. |
| L3 작업 문맥 | 현재 후보와 필요한 diff·스레드·대화 발췌만 로드하고 작업 종료 시 해제한다. |

로컬 Python 작업 큐가 실행·분기·재시도·병합을 관리하는 구조를 제안한다. 수집은 읽기 전용 GitHub CLI/API와 로컬 Git, 원본은 `data/raw/{github,chatgpt}/`, 검색·관계·상태는 SQLite에 둔다. ChatGPT 전체 내보내기는 vault 및 동기화 대상과 분리한다. FTS5로 식별자와 오류 문구를 우선 찾고, 의미가 유사한 대화에는 로컬 벡터 검색을 보완적으로 적용한다. 심층 조사에 선정된 버전·파일에만 Tree-sitter 정의·참조·호출 관계를 확장한다. SQLite에서 PR↔커밋·리뷰, 후보↔메시지·근거를 연결한다. 더 복잡한 워크플로 도구는 분기·재시도가 실제로 필요할 때 검토한다.

PR 발굴, 리뷰 분석, 코드 진화 조사, 대화 연결, 행동 패턴 분석, 독립 검증, 노트 작성을 논리적으로 분리한다. 필요한 역할만 호출하며, 전달 객체에는 프로젝트·후보 ID, 관찰 사실, 가설, 근거 ID, 다음 작업을 담는다. 검증자는 앞선 해석을 물려받지 않고 원본을 조회한다. 작업별 문맥 예산을 두고 큰 PR은 스레드·기능·파일 묶음으로 분할한다. 묶음 간 관계와 미검토 범위를 병합할 때 확인한다. 롤링 요약은 위치 안내와 복구에 쓰고 최종 주장마다 원본을 다시 연다.

## 8. 세션 인계 계약

ChatGPT 프로젝트 하나에서 총괄·프로젝트별 검토 채팅을 나누고, Codex 채팅은 구현·수집·프로젝트별 분석처럼 승인된 작업 단위로 나눈다. 두 환경에 같은 버전의 명세와 템플릿을 둔다. 작업 공간과 ChatGPT 프로젝트 파일이 자동으로 일치한다고 가정하지 않는다.

체크포인트에는 명세·분석·모델·프롬프트 버전, 프로젝트와 범위, 승인 근거와 유효 범위, 입력 해시, 처리 단계, 완료 ID와 산출물 경로, 다음 큐 항목, 페이지 커서, 실패·누락, 대기 질문·실험 승인 상태를 남긴다. 후보·근거 ID로 중복을 방지하고 결과 저장과 완료 표시는 함께 확정한다. 중단된 항목은 원본과 완료 기록을 대조한 뒤 재시도한다. 다음 채팅은 체크포인트가 가리키는 원본을 열어 마지막 완료 단위와 다음 작업을 확인한다.

**기준 원본의 인계 상태 (2026-11-12, 역사적 기록).** 세 명세 작성만 수행했다. 수집·분석·벤치마크는 시작 전이며 데이터베이스, 인덱스, 작업 큐, 분석 결과와 Obsidian 노트는 아직 없다. 다음 계획 작업은 필요한 입력·권한, 구성요소 의존 순서, 첫 구현 단계의 변경 범위와 완료 기준을 제시하는 것이다. 실제 구현·분석은 해당 단계의 승인 후 진행한다.

위 역사적 상태를 현재 구현 부재나 과거 승인 취소로 해석하지 않는다. 현재 현황은 6.1절, 문서 적용 범위와 재개 조건은 13절을 따른다.

## 10. 변경 통제와 결정 이력

새 요청은 기존 설계를 대체하라는 명시적 지시가 없는 한 호환되는 확장으로 우선 해석한다. 단, 호환된다고 단정하기 전에 관련 원문과 ID를 대조한다.

| --- | --- | --- |

절차:

1. 원본 명세·정본 버전·승인 기록·체크포인트를 직접 읽고 관련 결정을 찾는다. 누락되거나 최신 여부가 불명확하면 해당 실행을 보류한다. ‘없음’과 ‘찾지 못함’을 구별한다.
2. 작업별로 `관련 결정 ID / 원문 위치 / 변경 전 / 제안 후 / 변경 유형 / 근거 / 영향 / 승인 필요 여부·근거 / 실행 가능 범위` 대조 보고를 먼저 남긴다. 이번 C00-A의 선행 보고는 [적용 전 대조](revisions/2026-11-14-c00-a1/PRE_APPLY_REPORT.md)다. Work 당시 보고서는 [보존 보고서](revisions/2026-11-14-r1/REVISION_REPORT.md)로 구분한다.
3. 영향 평가에는 수집 완전성·제외와 개인정보 범위·기여 귀속·검증 독립성·단계 순서·기존 데이터·노트·진행 작업·재처리·호환성·복구를 포함한다. 해당 없음도 이유를 적는다.
4. 변경 승인에는 대상 결정·허용 행위·입출력·단계·유효 조건·사용자 발언 위치·시점을 연결한다. 설계 수용, 문서 개정, 구현, 자료 접근, 분석, 실험 승인을 구별한다. 불명확한 권한을 포괄 승인으로 해석하지 않는다.
5. 승인된 범위만 사본에 반영하고 원본 대비 diff와 보호 결정 보존을 검증한다. 충돌이 해소되지 않은 부분은 확정 명세로 쓰지 않는다.
6. 이력을 추가한다. 기존 결정을 조용히 덮어쓰거나 행을 삭제하지 않는다. 실질적 교체는 새 결정 ID를 발급하고 이전 ID를 `superseded`로 표시하면서 이전 문구·근거·이력 또는 보존 사본 경로를 유지한다. 영향받는 작업을 찾아 재검토·재검증 범위를 지정한다.
7. 인계 시 사본·정본 적용 여부, 승인, 미완료를 함께 기록한다. 문서 전달은 동기화 원본 교체나 실행 승인과 별개다.

결정 상태는 `proposed`(제안), `approved`(사용자 확정), `superseded`(후속 승인으로 대체), `conflict/pending`(충돌·미확정)으로 관리한다. 구현 상태와 따로 적는다. 기존 승인 시점이 모르면 ‘기존 명세에 기록, 정확한 일시 미확인’으로 남긴다.

## 11. 자동 검증 도입 계획 · 미구현

기존 Python 작업 큐와 SQLite 설계를 확장한다. 새 오케스트레이션 체계로 교체하지 않는다. GOV-03의 공통 자동 검증 계획은 문서로 정의되었으나 구현 미완료다. 기존 큐·SQLite 자체는 이미 구현되어 있다(6.1절). 이번 C00-A는 계획의 정본 반영만 승인하며 프로그램·DB 변경이나 실제 입력에 대한 자동 처리 실행은 하지 않는다.

## 12. Codex 세션과 논리적 분석 역할

Codex 세션은 승인된 구현·수집·분석을 수행하는 작업 실행 단위다. 논리적 분석 역할은 ARCH-02의 독립 책임 단위다. 세션 수와 역할 수는 일대일 대응하지 않으며, 한 세션이 여러 책임을 맡더라도 역할별 입력·출력·관점을 구분하고 독립 검증을 약화하지 않는다. 검증자는 원본을 새로 조회한다.

선행 구현 작업을 분석 단계로 재번호 매겨 7절을 대체하지 않는다. 기존 5단계와 프로젝트 간 개인 특성 분석을 독립적으로 유지한다. 세션 분할·동시 실행·각 완료 기준은 향후 승인된 작업안에서 의존성과 관련 결정 ID를 대조해 확정한다.
